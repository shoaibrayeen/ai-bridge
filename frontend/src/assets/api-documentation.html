Quick start

Three calls, end to end

Exchange your API key for a token, find out which models you can call, then call one. Everything under /v1 and /admin/api needs the token; POST /api/auth/token is the only open endpoint.

# 1. Get a token
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"api_key": "YOUR_AIBRIDGE_API_KEY"}' | jq -r .token)

# 2. See what you can call
curl -s http://localhost:8080/v1/models \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-Tenant-ID: acme' | jq

# 3. Call it
curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-Tenant-ID: acme' \
  -H 'X-Feature: chat' \
  -H 'Content-Type: application/json' \
  -d '{"messages": [{"role": "user", "content": "Hello"}]}' | jq

The two headers that decide routing

HeaderRequiredWhat it does
X-FeatureYes, unless model names a gateway configSelects the failover chain. A label you define, e.g. chat, summarization
X-Tenant-IDNoPrefers this tenant's configs over the global ones. Omit to use global only
X-Request-IDNoYour correlation id. Generated if absent; always echoed back
X-Include-LineageNotrue returns the routing trail in the response body

Your consumers hold one credential. They present the AIBridge API key and get a bearer token. Provider keys (OpenAI, Anthropic, AWS, IBM) stay encrypted in the gateway's database and are never exposed through any endpoint — admin reads return a mask.

Auth

One open endpoint

POST /api/auth/token no auth

Exchanges the static API key for an opaque bearer token.

Request body

{
  "api_key": "YOUR_AIBRIDGE_API_KEY"
}

200 — Response

{
  "token": "bd9591b0-61b2-48dc-8d74-88a802b6d4b0",
  "expires_in_minutes": 60
}

Then, on every other call

Authorization: Bearer bd9591b0-61b2-48dc-8d74-88a802b6d4b0

Errors

400api_key missing or blank
401Wrong key — or the caller is locked out

Brute-force limiting. Failures are counted per caller for 5 minutes. After 10, the caller is refused even with the correct key, and the lockout window is rolling — a persistent attacker never ages out of it. A locked-out caller and a wrong key return an identical 401, so probing reveals nothing.

Chat completions

The endpoint your application calls

POST /v1/chat/completions bearer

Standard OpenAI Chat Completions format in and out.

Request body

{
  "messages": [
    {"role": "system",  "content": "You are concise."},
    {"role": "user",    "content": "Explain token buckets in one sentence."}
  ],
  "temperature": 0.7,
  "max_tokens": 200,
  "top_p": 1,
  "stream": false
}

Body fields

FieldTypeNotes
messagesrequiredarrayEach item is {"role": "system"|"user"|"assistant", "content": "..."}
modelstringIgnored unless it is a gateway model name — see below
streambooleantrue switches the response to SSE
temperaturenumberOptional. Your value wins; otherwise the config's stored default is used; otherwise the field is omitted entirely so the provider applies its own default
max_tokensinteger
top_pnumber
ninteger
stoparray
presence_penaltynumber
frequency_penaltynumber

200 — Response

{
  "id": "chatcmpl-9c1f...",
  "object": "chat.completion",
  "created": 1789151540,
  "model": "ai-bridge-1-claude-sonnet-6",
  "choices": [
    {
      "index": 0,
      "message": {"role": "assistant", "content": "A token bucket refills at a fixed rate..."},
      "finish_reason": "stop"
    }
  ],
  "usage": {"prompt_tokens": 41, "completion_tokens": 96, "total_tokens": 137}
}

model in the response is always the gateway name, never the provider's. Send that value back in a later request and you reach the same config.

Choosing the LLM

model in the bodyWhat happensFailover
Absent, or a provider name like gpt-4oIgnored. Routed by X-Tenant-ID × X-FeatureYes full chain
A gateway name like ai-bridge-2-claude-sonnet-6Pinned to exactly that config. X-Feature becomes optionalNo you asked for one

OpenAI SDKs require a non-empty model, so sending a provider name is safe — it simply falls through to feature routing rather than erroring.

# Feature routing — walks the failover chain
curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-Tenant-ID: acme' -H 'X-Feature: chat' \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"Hello"}]}'

# Pinned to one config — no failover
curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-Tenant-ID: acme' \
  -H 'Content-Type: application/json' \
  -d '{"model":"ai-bridge-2-claude-sonnet-6",
       "messages":[{"role":"user","content":"Hello"}]}'

The failover chain

Feature routing resolves an ordered chain and walks it. Three conditions advance to the next link:

OrderConfig
1Tenant primary — lowest priority wins
2Tenant fallback
3Global primary
4Global fallback
ConditionAdvances?
Waited past the config's queue_timeout_ms for a pacing slotYes
Provider returned 429Yes
Provider returned 5xx or timed outYes
Provider answered 200 with no contentNo — returned to you as 200 with empty content
Misconfiguration, e.g. a bad encryption keyNo — it would fail identically on every config, so the error is raised

If every link is exhausted, the gateway returns 502.

Streaming

Server-sent events

Set "stream": true. The response becomes text/event-stream — one data: line per chunk, terminated by data: [DONE].

curl -N http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-Feature: chat' -H 'Content-Type: application/json' \
  -d '{"stream": true, "messages": [{"role":"user","content":"Hello"}]}'

Response

data: {"id":"chatcmpl-x","object":"chat.completion.chunk","model":"ai-bridge-1-gpt-4o","choices":[{"index":0,"delta":{"role":"assistant"}}]}

data: {"id":"chatcmpl-x","object":"chat.completion.chunk","model":"ai-bridge-1-gpt-4o","choices":[{"index":0,"delta":{"content":"Hel"}}]}

data: {"id":"chatcmpl-x","object":"chat.completion.chunk","model":"ai-bridge-1-gpt-4o","choices":[{"index":0,"delta":{"content":"lo"}}]}

data: {"id":"chatcmpl-x","object":"chat.completion.chunk","model":"ai-bridge-1-gpt-4o","choices":[{"index":0,"delta":{},"finish_reason":"stop"}],"usage":{"prompt_tokens":9,"completion_tokens":5,"total_tokens":14}}

data: [DONE]

Streaming works against every provider, but the experience differs:

ProvidersBehaviour
OpenAI, Cerebras, ClaudeNative tokens forwarded as the provider emits them
watsonx.ai, BedrockBuffered the gateway makes the blocking call and emits the answer as one content chunk

Both produce an identical, well-formed stream — your client needs no branching. The difference is time to first token.

Failover stops at the first byte. Acquiring a pacing slot and getting the provider to start answering are retried down the chain. Once the first chunk has reached you, bytes are on the wire and there is no honest way to switch providers, so a mid-stream failure ends the stream.

Token counts arrive last. usage rides on the terminating chunk.

Lineage

Which providers were tried, and what each cost

Every completion records the path it took. It is always written to the log against the request id; send X-Include-Lineage: true to get it in the response body too, under x_aibridge_lineage.

curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H 'X-Feature: chat' -H 'X-Include-Lineage: true' \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"Hello"}]}'
"x_aibridge_lineage": {
  "request_id": "8f3c1e20-...",
  "tenant_id": "acme",
  "feature": "chat",
  "routing": "feature",
  "chain_length": 2,
  "attempts": [
    {"sequence": 1, "gateway_model_name": "ai-bridge-1-gpt-4o",
     "model_name": "gpt-4o", "provider": "OPENAI",
     "outcome": "QUEUE_TIMEOUT", "duration_ms": 5001,
     "detail": "..."},
    {"sequence": 2, "gateway_model_name": "ai-bridge-1-claude-sonnet-6",
     "model_name": "claude-sonnet-6", "provider": "CLAUDE",
     "outcome": "SUCCESS", "duration_ms": 812,
     "prompt_tokens": 41, "completion_tokens": 96, "total_tokens": 137}
  ],
  "total_duration_ms": 5813,
  "billed_total_tokens": 137
}
outcomeMeaning
SUCCESSProvider answered with usable content
EMPTY_RESPONSEAnswered 200 with no content — returned to you as-is
QUEUE_TIMEOUTNo pacing slot within the config's timeout
RATE_LIMITEDProvider returned 429
UNAVAILABLEProvider returned 5xx, or the call timed out
NO_ADAPTERNo adapter registered for that provider
ERRORMisconfiguration or bug — recorded, logged and raised, never failed over

billed_total_tokens sums every attempt, not just the successful one, so tokens burned by a provider that later failed over stay visible.

Models

OpenAI-compatible discovery

Each config gets a service-wide unique name, ai-bridge-<sequence>-<model>. The sequence counts up per model, which is what lets the same model be registered more than once — two Claude Sonnet 6 configs with different keys or rate limits become ai-bridge-1-claude-sonnet-6 and ai-bridge-2-claude-sonnet-6.

GET /v1/models bearer

Every model this tenant may call: its own configs plus the global ones.

200 — Response

{
  "object": "list",
  "data": [
    {
      "id": "ai-bridge-1-claude-sonnet-6",
      "object": "model",
      "created": 1789151540,
      "owned_by": "claude",
      "root": "claude-sonnet-6",
      "features": ["chat"]
    },
    {
      "id": "ai-bridge-2-claude-sonnet-6",
      "object": "model",
      "created": 1789151540,
      "owned_by": "claude",
      "root": "claude-sonnet-6",
      "features": ["summarization"]
    }
  ]
}

root is the provider's own model name behind the gateway id. features is an AIBridge extension; OpenAI clients ignore it.

GET /v1/models/{gateway-model-name} bearer

One model. A config owned by another tenant returns 404, identical to one that does not exist — you cannot probe for other tenants' configuration.

Admin: providers

Register a provider type once

A provider row says how to authenticate. Configs point at it.

auth_typeCredentials you store on the configWhat the gateway does
API_KEY{"api_key": "sk-..."}Sends it directly — Authorization: Bearer, or x-api-key for Claude
IAM_TOKEN{"api_key": "..."} + extra_params.project_idExchanges the key at auth_endpoint for a bearer token, caches it until it nears expiry
AWS_SIGV4{"access_key_id": "...", "secret_access_key": "...", "session_token": "..."} + extra_params.regionSigns each request with SigV4; nothing cached, every signature is request-specific
OAUTH2—Reserved in the schema; no adapter uses it yet
POST /admin/api/llm-providers bearer

Request body

{
  "name": "WATSONX",
  "auth_type": "IAM_TOKEN",
  "auth_endpoint": "https://iam.cloud.ibm.com/identity/token"
}

name must be one of OPENAI, CEREBRAS, CLAUDE, WATSONX, BEDROCK — uppercase. auth_endpoint is only needed for IAM_TOKEN.

201 — Response

{
  "id": "7c2f9a10-...",
  "name": "WATSONX",
  "auth_type": "IAM_TOKEN",
  "auth_endpoint": "https://iam.cloud.ibm.com/identity/token"
}
GET /admin/api/llm-providers bearer

All providers. GET /{id} for one, PUT /{id} to update, DELETE /{id} to remove.

Admin: configs

Where models, credentials and rate limits live

POST /admin/api/llm-configs bearer

Creates a config. The gateway makes a real completion call to the provider before persisting anything — a wrong key, a wrong region or a nonexistent model comes back as 422 with the provider's own message, rather than failing at your first real request.

Request body

{
  "tenant_id": "acme",
  "provider_id": "7c2f9a10-...",
  "model_name": "claude-sonnet-6",
  "endpoint_url": "https://api.anthropic.com/v1/messages",
  "credentials": "{\"api_key\": \"sk-ant-...\"}",
  "features": ["chat", "summarization"],

  "rps_limit": 5,
  "rpm_limit": 200,
  "tpm_limit": 100000,
  "queue_timeout_ms": 5000,

  "default_temperature": 0.7,
  "default_max_tokens": 1024,
  "default_top_p": 1.0,

  "is_fallback": false,
  "priority": 0,
  "extra_params": "{\"project_id\": \"...\"}"
}

Fields

FieldNotes
provider_idrequiredFrom GET /admin/api/llm-providers
model_namerequiredThe provider's own name. The gateway name is derived from it
endpoint_urlrequiredMust pass the SSRF allowlist. HTTPS outside dev
credentialsrequiredJSON string, shape depends on auth_type. Encrypted with AES-256-GCM before storage
tenant_idOmit for a global config every tenant can use
featuresLabels callers send in X-Feature
rps_limit / rpm_limit / tpm_limitNull means unlimited. Each creates its own token bucket
queue_timeout_msHow long a request waits for a slot before failing over. Default 5000
default_*Used when the caller omits that parameter
is_fallbacktrue places this after the primaries in the chain
priorityLower wins among configs at the same level
extra_paramsJSON string. project_id for watsonx, region for Bedrock

201 — Response

{
  "id": "3f9a2c41-...",
  "model_name": "claude-sonnet-6",
  "gateway_model_name": "ai-bridge-1-claude-sonnet-6",
  "tenant_id": "acme",
  "provider_name": "CLAUDE",
  "credentials": "****",
  "features": ["chat", "summarization"],
  "rps_limit": 5,
  "is_active": true,
  "created_at": "2026-09-12T04:12:00Z"
}

Note gateway_model_name — that is what callers put in the model field. Credentials come back masked, always.

Errors

400Endpoint failed the SSRF allowlist, or plain HTTP outside dev
404provider_id does not exist
422The live validation call to the provider failed — message included
POST /admin/api/llm-configs/test bearer

Same body as create, but nothing is saved — a dry run to check credentials before committing.

{"valid": true, "latency_ms": 412}
GET /admin/api/llm-configs bearer

Filterable: ?tenant_id=acme&feature=chat&provider_id=.... Credentials masked.

PUT /admin/api/llm-configs/{id} bearer

Re-validates against the provider before saving. Send the masked credentials value back unchanged to keep the stored secret; send a new value to replace it.

Changing model_name assigns a new gateway model name. Changing anything else leaves it alone, so clients pinning the name are not broken by an unrelated edit.

DELETE /admin/api/llm-configs/{id} bearer

Soft delete — sets is_active = false. The row and its encrypted credentials survive, so the config can be put back into rotation. Returns 204.

Admin: features, load test, health

Operations

GET /admin/api/features bearer

Distinct feature labels currently in use — the valid values for X-Feature.

["chat", "summarization", "code-gen"]
POST /admin/api/load-test bearer

Starts a load test. Returns 202 immediately with a run id; poll for results.

Request body

{
  "tenant_id": "acme",
  "feature": "chat",
  "total_requests": 100,
  "parallel": 10,
  "prompt": "Say hello"
}

202 — Response

{"run_id": "b81c4f22-..."}

Then GET /admin/api/load-test/{run_id} for progress and results, or GET /admin/api/load-test for recent runs. parallel is capped by AIBRIDGE_LOAD_TEST_MAX_PARALLEL (default 500).

GET /admin/api/health bearer

Database and cache health with measured latency. For unauthenticated probes suitable for Kubernetes, use /q/health/live and /q/health/ready instead.

Errors

One envelope everywhere

Every error shares one shape, so a client can branch on error.status without parsing prose:

{
  "error": {
    "type": "ConfigNotFound",
    "message": "No configuration found for tenant='acme' and feature='chat'",
    "status": 404
  }
}
statustypeCause
400BadRequestMissing X-Feature, malformed header, or a disallowed endpoint URL
400ConstraintViolationBody failed validation; the response lists each violations[] entry
401UnauthorizedMissing, invalid or expired bearer token
404ConfigNotFoundNo active config for this tenant and feature, or an unknown gateway model name
404NotFoundNo such path
422LlmValidationThe live validation call to the provider failed
500EncryptionEncryption key missing, wrong length, or rotated away from the stored data
502ProviderUnavailableEvery config in the failover chain was exhausted

Every response carries X-Request-ID. Quote it when reporting a problem — the gateway logs the full routing lineage against it, including which providers were tried and why each failed.
