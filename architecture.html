System topology

What talks to what

Two kinds of caller reach the same Quarkus process. A client application posts OpenAI-format chat completions and identifies itself with headers; the admin SPA bundled into the same JAR manages configuration and runs load tests. Both pass through one filter chain, land in one service layer, and fan out through the adapter layer to whichever provider the database says this tenant and feature should use.

Request lifecycle

Five steps, three ways to fail over

A chat completion is not routed by the model field — that field is ignored and the model comes from the database row. Routing is decided entirely by the X-Tenant-ID and X-Feature headers, which resolve to an ordered chain of configs. The gateway walks that chain, and three distinct conditions make it advance to the next link.

What advances the chain

Config resolution

How the chain is built

One lookup produces the whole failover chain, in priority order. A tenant's own configuration is preferred over the global default, and within each scope the primary is preferred over the fallback. The result is cached for five minutes under llm_config:{tenant}:{feature} and invalidated whenever an admin writes to any config that touches that feature.

Ordertenant_idis_fallbackMeaning
1= TfalseTenant primary — lowest priority value wins
2= TtrueTenant's own fallback provider

4IS NULLtrueGlobal fallback — last resort

Only rows with is_active = true are considered, which makes admin deletion a soft deactivation rather than a destructive write — a config can be pulled out of rotation and put back without losing its encrypted credentials.

Why the model name is server-side. Callers send a feature, not a model. That lets an operator move summarization from GPT-4o to Claude, or add a Cerebras fallback behind it, with a single admin write and no client deployment. It also means a compromised client cannot pick an expensive model.

Rate pacing

Queue rather than reject

When a caller exceeds a provider's rate limit, the gateway does not return 429. It holds the request and dispatches it as soon as a token is available — and only gives up, in favour of the next provider in the chain, once the wait exceeds that config's queue_timeout_ms. Each config gets up to three independent token buckets, created only for the limits that are actually set.

Token accounting

RPS and RPM are debited before the call. TPM cannot be: the real token cost is only known once the provider answers, so the gateway debits an estimate up front and calls reconcileTokens with the actual usage from the response, correcting the bucket after the fact.

Provider adapters

One interface, five dialects

Every adapter implements the same two-method interface and is selected from a CDI-populated map keyed by provider name. The gateway's internal representation is always the OpenAI shape; each adapter owns the translation in both directions, including whatever authentication ritual the provider demands.

Parameter merge

Before any adapter sees the request, optional generation parameters are resolved three ways in order: the value in the caller's payload wins; otherwise the config's stored default is used; otherwise the parameter is omitted entirely so the provider applies its own default. Omission is deliberate — sending temperature: 0 because nothing was configured would silently change model behaviour.

Data model

Three tables, one migration

Flyway owns the schema; V1__init_schema.sql runs at startup. The shape is small on purpose — provider types, per-tenant configuration, and the feature labels that point at them.

TableCarriesKey constraint
llm_providerProvider type and its auth mechanism, plus an optional auth endpoint for token exchange—
llm_configModel name, endpoint, encrypted credentials, rate limits, generation defaults, priority, fallback flag, provider-specific extra_paramsUNIQUE (tenant_id, model_name, is_fallback)
featuresFeature labels attached to a config, cascade-deleted with itUNIQUE (llm_config_id, feature)

Credentials are never stored in the clear: the whole credential blob is AES-256 encrypted with aibridge.encryption.key before it reaches the column, and admin reads return a masked value. Rotating that key requires re-encrypting every row — it is not a value to change casually.

Validation on write

Creating or updating a config does not simply persist it. The admin API first asks the matching adapter to make a real completion call with a trivial prompt; only a successful provider response allows the row to be written. A bad key, an unreachable endpoint or a nonexistent model comes back as 422 with the provider's own reason, rather than as a runtime failure at the first real request.

Cache & state

The one decision that constrains scaling

Everything that isn't in PostgreSQL lives behind a CacheProvider interface with two implementations, chosen at startup by the cache.mode property. This is the single knob that decides whether the gateway can run as more than one instance.

cache.modeBacked byRate limits areSuitable for
in-memory defaultIn-process mapPer JVM — two replicas allow double the trafficLocal development, single-instance deploys
redisRedis 7Shared — the limit is the real limitAny horizontally scaled deployment

Admin sessions live in the same cache. Bearer tokens issued by POST /api/auth/token are stored under aibridge:api_token:{token}. In in-memory mode, a restart logs every admin out, and behind a load balancer a token minted by one replica is unknown to the others.

Security posture

What the edge enforces

The gateway holds every tenant's provider credentials and makes outbound calls on their behalf, which makes two risks specific to it: credential exposure and server-side request forgery.

Deployment

One image, three services

The image is built in three stages: Node compiles the Angular bundle straight into the Maven resource tree, Maven packages the Quarkus fast-jar around it, and a JRE base runs it as a non-root user. Nothing but Docker is needed on the build host.

Configuration precedence

Quarkus reads configuration from several sources; the first one that defines a property wins.

RankSourceTypical use
1System properties (-D…)One-off overrides, -Dui.required=true at build time
2Environment variablesContainer and CI configuration
3.env in the working directoryLocal development secrets
4application.propertiesDefaults, including %docker and %prod profiles

Property names map to environment variables by uppercasing and replacing every non-alphanumeric character with an underscore: quarkus.datasource.jdbc.url becomes QUARKUS_DATASOURCE_JDBC_URL, aibridge.encryption.key becomes AIBRIDGE_ENCRYPTION_KEY.

Build on JDK 17 or 21. Quarkus 3.17.5 bundles a Byte Buddy that supports class files up to Java 23. A newer JDK compiles the sources fine and then fails in Quarkus augmentation, which makes the error look like a code problem when it is a toolchain one.
